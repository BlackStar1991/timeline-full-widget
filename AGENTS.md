## 2. Current architecture and non-negotiable boundaries

- WordPress plugin slug and translation domain: `timeline-full-widget`; namespaced PHP prefix: `TimelineFullWidget\`.
- Gutenberg block names are public persisted identifiers: `za/timeline-full-widget`, `za/timeline-item`, `za/timeline-item-side`, and `za/timeline-item-content`. Do not rename them.
- The item structure introduced in 3.0.0 uses separate nested **side** and **main content** block areas. The default main area starts with a level-three Heading (`.tl-title`) and a Paragraph, but users may add other compatible blocks.
- `src/item/deprecated-v2-save.js` and `src/item/legacy-title-migration.js` preserve older serialized content. `src/block-template-compat.js` supports editor versions with and without static block-type templates. Remove these only with a tested migration/deprecation plan, not because they look unused.
- PHP `includes/` classes are autoloaded. `timeline-full-widget.php` is the bootstrap; `elementor-timeline-widget.php` is an intentional compatibility entry point. Global `TimelinePlugin` and old `TIMELINE_*` aliases remain public compatibility APIs, **not dead application code**. Delete only after a major-version deprecation and documented consumer migration, never as a cosmetic cleanup.
- Elementor integration must remain optional: activating the plugin without Elementor must not fatal. The Elementor widget extends `Elementor\Widget_Base` and must be loaded only when Elementor is available.
- Do not create overlapping asset registrations, duplicate frontend animations, or global CSS leaking into unrelated WordPress pages.

## 3. Shared styles across Gutenberg, Elementor, and Classic Editor

**Current state (important): sharing CSS/DOM conventions is implemented; a single cross-editor **persisted** settings schema or live style state does NOT exist. The portable v1 format supports explicit, best-effort conversion in both directions, not universal editor style parity.** Do not describe it as universal style synchronization or invent a migration layer.

1. **Canonical shared styling layer:** `assets/css/core/style.css`. It defines timeline structure, responsive layout, marker/line rendering, and fallback variables. Gutenberg imports it in `src/index.js`, so its contents are emitted into `build/style-index.css`; Elementor and Classic Editor load the original CSS. On `init`, `AssetManager::registerAssets()` registers the `timeline-core-style` handle. The Elementor widget declares it in `get_style_depends()`: **do not re-add a global `elementor/frontend/after_enqueue_styles` hook** or enqueue this stylesheet on every Elementor frontend page. Classic enqueues it only on eligible Classic screens. Gutenberg already has its compiled copy; do not enqueue the raw CSS again in the block editor.
2. **Gutenberg style adapter:** `src/timeline-style.js` maps block attributes to CSS variables on `.timeline-wrapper`; `src/edit.js` and `src/save.js` must stay consistent. Gutenberg-only `src/style.scss` / `src/editor.scss` should not silently become the sole place for a rule Elementor needs.
3. **Elementor style adapter:** `includes/Elementor/TimelineWidget.php` maps its **different** control IDs to the same CSS variables through Elementor `selectors`. In 3.3.3 duplicate inline wrapper custom properties were removed so selector-generated CSS stays authoritative for **live editor updates**. Do not reintroduce competing inline defaults or PHP/Underscore template overrides for these variables.
4. **Shared frontend runtime:** `assets/js/core/animation.js` is imported by the Gutenberg, Elementor, and Classic adapters. Preserve its DOM hooks and initialization/teardown behavior across builders; do not fork the animation algorithm per editor.
5. **Stable DOM contract:** maintain `.wp-block-za-timeline-full-widget`, `.timeline-wrapper`, `.timeline`, `.timeline-item`, `.tl-mark`, `.tl-trigger`, `.timeline-side`, `.timeline-panel`, `.tl-title`, `.timeline-line-animation`, and relevant state/layout classes. Elementor deliberately emits Gutenberg-compatible wrapper and item classes; it does not serialize Gutenberg `InnerBlocks`.
6. **Public CSS variable contract:**
   - `--timeline-line-color` (default `#F6F6F8`)
   - `--timeline-line-width` (default `4px`)
   - `--timeline-marker-color` (default `#F6F6F8`)
   - `--marker-size` (default `30px`)
   - `--timeline-line-active-color` (default `#F37321`)
   - `--timeline-marker-active-color` (default `#F37321`)
   Change spelling, units, or fallback behavior only with a cross-editor compatibility check.

### Style inheritance is **not** the same in both editors

- **Gutenberg (3.3.1+):** a newly inserted Timeline Item *initially copies* inheritable style/layout attributes from the preceding item. Items remain independently editable afterward. The manual **Apply item styles to other items** action remains available. Logic is in `src/edit.js`, `src/item/edit.js`, and `src/item/style-inheritance.js` (including protected content/media/ID fields and descendant block matching). Do **not** restore continuous parent-to-child style syncing or blindly copy content/identifiers.
- **Elementor:** the widget has shared item controls. Individual repeater items default to `inherit_item_styles = yes` and may opt out for unique style overrides (`timeline-item-unique-style`). Both the PHP `render()` and Underscore.js `content_template()` must apply identical defaults, class names, selectors, alignment, content-layout, and media-order logic. This is **widget-level inheritance**, not Gutenberg's one-time copy behavior.
- **Shared semantic style mapping (4.0.0):** `STYLE_KEYS` in `assets/js/transfer/transfer-core.js` maps the canonical `lineColor`, `lineWidth`, `markerColor`, `markerSize`, `animationLineColor`, and `animationMarkerColor` to *existing* Gutenberg and Elementor keys. Keep it aligned with real Elementor controls and `block.json`, never rename persisted keys without migrations. This **does not** convert arbitrary content or Advanced style settings between editors.

### Required regression matrix for any shared style or markup change

Check both the editor preview and saved frontend for Gutenberg **and** Elementor: line color/width, marker color/size, animated colors, numeric marker centering, title color/alignment, content and opposite-side alignment, horizontal/reversed media layout, independent item overrides, sticky/animation state, narrow container and mobile behavior. Verify Elementor selector changes update *immediately* without switching controls or reloading. Also smoke-test Classic Editor output when core CSS or animation changes.

### Gutenberg editor scroll coordination (October 16, 2026)

The animation source of truth remains `assets/js/core/animation.js`. The Gutenberg `build/index.js` embeds a compiled copy of that runtime; changes must be reflected in **both** the source and compiled editor, ideally by running `npm run build`. During this patch, the existing build was updated to match because npm dependencies were not installed in the verification environment. Do not leave the build/source pair divergent or rely solely on frontend animation tests.

Gutenberg can scroll either **inside its iframe** or in a **scrolling element of the editor's parent document**. Use local viewport coordinates for the former and projected iframe-to-parent coordinates for the latter. Never apply parent viewport geometry while the iframe has its own scroll root. `assets/js/adapters/gutenberg-editor-scroll-bridge.js` is a classic, editor-only script that captures parent-document scroll events and forwards a `za-timeline-editor-scroll` event to same-origin Timeline iframes. The core animation listens to that event and cleans it up on teardown. This avoids fragile cross-realm DOM callbacks. Keep the bridge out of frontend/Elementor assets and prevent duplicate initialization. Tests: `npm run test:animation`; browser smoke: scroll the Gutenberg canvas with a 2+ item Timeline and verify line/markers without selecting blocks. Distinguish core `BlockBindingsAttributeControl` / external AI editor warnings from errors thrown by our own code.

## 4. Portable Timeline v1 contract (versions 4.0.0–4.0.0)

- **No editor coupling.** Pure transfer logic is in `assets/js/transfer/transfer-core.js` (ES module). Its sibling `package.json` scopes module semantics for Node tests. The Gutenberg editor-only sidecar `assets/js/transfer/gutenberg-editor.js` registers one `editor.BlockEdit` filter and is only enqueued through `AssetManager::enqueueGutenbergTransferAssets()`. Elementor's widget (`includes/Elementor/TimelineWidget.php`) adds the Content-tab RAW_HTML controls; `assets/js/transfer/elementor-editor.js` binds their actions after a classic `elementor-editor-loader.js` dynamically imports it; the classic loader is enqueued through `enqueueElementorEditorAssets()` **only in Elementor editor**. Both adapters import the **single shared DOM modal** from `assets/js/transfer/import-dialog.js`. Do not enqueue either editor transfer adapter on frontend or Classic Editor.
- **Preserved Gutenberg build:** the transfer controls are a sidebar sidecar using official `wp.*` APIs, and intentionally does not require editing `src/index.js` or bundled `build/index.js`. When updating the main block's `src/`, still run `npm run build`; never hand-edit bundled assets. A future migration of transfer code into `src/` must remove the sidecar hookup so the inspector never duplicates.
- **Portable envelope:** `format: 'timeline-full-widget'`, `schemaVersion: 1`, `origin: 'elementor'|'gutenberg'`, `elementType`, `pluginVersion`, `mediaPolicy: 'placeholder-only'`, `exportedAt`, `data`. Files use `timeline-elementor-YYYY-MM-DD-v1.tfw.json` or `timeline-gutenberg-YYYY-MM-DD-v1.tfw.json`. Bump the **schema version** with explicit migration when breaking format changes; plugin versions and schema versions are independent. Never silently accept future unknown schema versions.
- **Native same-editor format and explicit cross-editor bridge:** Elementor `data` is its *full native settings object* (including Advanced properties, responsive settings, repeater `_id`, custom CSS, user classes), not a lossy design token subset. Gutenberg `data` contains root block name/attributes plus the **entire** recursively nested block tree, preserving content, typography, supports and item styles. In 4.0.2, Gutenberg files may also be imported into Elementor through the mapped `gutenbergToElementor()` adapter. Elementor-to-Gutenberg remains unsupported. Reject all other origin/destination combinations clearly and never imply arbitrary nested Gutenberg layouts convert losslessly.
- **Shared import confirmation (October 16, 2026):** Preserve one popup implementation in `assets/js/transfer/import-dialog.js`, shared by Gutenberg and Elementor. Gutenberg's inspector shows only Export / Import buttons, the hidden local JSON file input, and brief status/errors; **never restore the obsolete sidebar checkbox/confirmation form**. After `readTransferFile()` and `parseTransfer()` validate the file, open the shared dialog with its filename, source editor, count, warnings, and options. The pop-up's `onAccept` callback performs the existing import; `Cancel`, backdrop click or `Escape` must never update a block/widget. For invalid files, show errors in the sidebar without opening the modal. Display untrusted transfer filenames/warnings as `textContent` or text nodes only, never `innerHTML`. Keep focus inside the dialog and restore the previous focus on dismissal. Elementor must also consume the shared dialog; do not reintroduce an Elementor-only copy of this logic. Regression checks live in `scripts/tests/transfer-ui.mjs`.
- **Safe filtering:** `IMPORT_OPTIONS` controls independent margin, padding, gap, HTML IDs, custom classes, custom CSS, animations, links, responsive settings, typography, and backgrounds. All are included except **HTML IDs by default**; users may opt into IDs if they have checked for collisions. Elementor Repeater `_id` is **not an HTML ID**; never delete it because dynamic selectors such as `.elementor-repeater-item-<id>` depend on it. Media attachment IDs are intentionally reset to `0`; keep that numeric property for native Elementor media controls.
- **Media portability:** exported media URLs/IDs are replaced by the stable `tfw://media-placeholder` token; the destination editor resolves it to its own `assets/images/media-placeholder.svg`, never the donor's URL. Preserve explicit media width/height and marker size (e.g. 40×40) in native setting values. Preserve video **type** and poster preview; Elementor PHP render and Underscore preview both show an image when imported video has no playable source. Gutenberg retains video media type with a local poster and placeholder URL until a new video is selected. Preserve external **hyperlinks** unless the user deselects links; do not confuse links with images. Media inside core image/video/cover blocks, rich HTML, custom CSS, poster fields and Elementor media arrays must also be scrubbed.
- **Gutenberg replacement semantics:** call `replaceBlocks([clientId], [createBlock(parentName,attrs,children)])` to replace the **entire** parent Timeline. This remounts `src/edit.js` and avoids its initial *new sibling* style inheritance overwriting exported per-item styles. Do not swap only `InnerBlocks` without a regression test for this effect. Never inject arbitrary unregistered block types; restrict portable nested names to registered `core/*` and `za/timeline-*` blocks.
- **Validation and trust boundary:** reject JSON over 5MB, incompatible format/schema or unsupported editor conversion, excessive nesting/array sizes and dangerous prototype keys. Import into an existing selected widget/block is a privileged editor action and must require confirmation. Import does not read external URLs, does not make an AJAX call, and does not install external media. HTML and custom CSS from trusted editors may still reference external fonts, assets or plugin/global theme styling; render HTML through existing WordPress/Elementor sanitizers and do not claim pixel-perfect results where themes, fonts, Elementor global style tokens or responsive breakpoints differ.
- **Transfer content:** the import option `content` is enabled by default. Both Elementor and Gutenberg must copy donor heading, paragraph and nested-block content when enabled. When disabled, keep receiver text in matching destination blocks while applying selected incoming styles. For Elementor, preserve existing `list_title`, `list_content`, `side_content`, etc. by item index. Do not change the persisted schema or turn off content silently.
- **Cross-editor adapter (4.0.2–4.0.0):** Gutenberg -> Elementor import is supported for explicitly mapped shared controls in `gutenbergToElementor()`. Preserve original editor data in exported files; conversion happens only after full validation at import. The reverse direction (Elementor → Gutenberg) is implemented in `elementorToGutenberg()`: map only supported widget/repeater controls to valid parent/item/side/main Gutenberg block trees. Never treat raw Elementor settings as Gutenberg attributes. Preserve effective layout inheritance rules when translating per-item horizontal/reverse flags. Test both directions and round-trip same-editor snapshots. Never promise pixel-perfect conversion of arbitrary Gutenberg InnerBlocks, theme palette presets, or theme CSS: Elementor repeaters cannot represent every nested block.
- **Gutenberg RichText serialization (4.0.2):** `gutenberg-editor.js` must recursively convert `RichTextData.toHTMLString()` (or `wp.richText.toHTMLString()`) to HTML strings in exports. Otherwise `JSON.stringify` silently yields `{}` and loses content. Files exported by earlier 4.0.1 may contain empty `content` objects; accept them as empty and present a warning, defaulting to **not** replacing destination content. No JSON patch can reconstruct missing text; request a fresh export from the source website.
- **Validation exception:** `onTheOneSide` is a persisted **boolean** Gutenberg attribute, not an event handler. Permit only this exact key with a boolean. Continue rejecting `onclick`, `onerror`, any other `on*` HTML event name, and `__proto__`, `prototype`, `constructor`.
- **Critical Elementor bootstrap (4.0.4):** Elementor may rebuild `WP_Scripts`/`WP_Styles` after `init`: `enqueueElementorEditorAssets()` must re-register missing handles before enqueueing. **Elementor also sometimes prints widget or editor dependencies as classic scripts, bypassing or overriding `script_loader_tag`**. Never register an ES module with static imports directly under an Elementor-facing WordPress handle. `za-timeline-transfer-elementor-editor` points to `assets/js/transfer/elementor-editor-loader.js`; `za-timeline-elementor` points to `assets/js/adapters/elementor-loader.js`. Both are tiny **classic** scripts that use `import()` to load their respective ES modules, and must keep `document.currentScript.src` URL resolution and cache-version query. Keep other native ES modules on the dedicated `script_loader_tag` filter; Gutenberg transfer uses its own classic loader. Regressions must verify that Elementor handles are classic-safe, the entrypoint files exist, a real browser can parse and execute loaders as classic scripts, the dynamically imported modules load, and the editor click handler actually binds. The PHP script-tag filter by itself is *not* evidence that Elementor emits `type="module"`.
- **Critical Gutenberg transfer bootstrap (4.0.6):** do **not** enqueue the ES module `assets/js/transfer/gutenberg-editor.js` directly. Real WordPress installations may print that handle as `type="text/javascript"`, resulting in `Cannot use import statement outside a module` and a missing Import / Export panel. `enqueueGutenbergTransferAssets()` registers `gutenberg-editor-loader.js` as a classic script with explicit `wp-*` dependencies and before-inline local placeholder config; the loader dynamically imports `gutenberg-editor.js` after WordPress deps are available. Do **not** force `type="module"` for this handle in `addModuleTypeAttribute()`. Exercise this exact classic loading path in JS smoke tests and PHP registration tests.
- **Cross-editor color contract (4.0.5+):** Gutenberg background/text styles can use palette slugs (`backgroundColor`, `textColor`, `var:preset|color|slug`), which Elementor COLOR controls cannot consume as slugs. `resolveGutenbergColor()` translates standard WordPress preset slugs; new exports attach a size-limited, validated `palette` snapshot of **used** source theme colors. `gutenbergToElementor()` must map per-item background to `li_bg_color`, supported title and content colors to `item_title_color`/`item_content_color`, and individual title alignment to `item_title_alignment`, setting `inherit_item_styles=no` for overrides. Never mutate the donor JSON or copy remote media. Test the four-item 4.0.2 export format with standard preset colors, custom palette colors and selective `background:false`, plus dangerous palette rejection. Schema version remains 1; old snapshots without `palette` must import.
- **Blueprints:** `assets/blueprints/blueprint.json` intentionally installs the **published WordPress.org** plugin and becomes a 4.0 demonstration *after* release. For pre-publication testing, create a **Blueprint bundle ZIP** containing `blueprint.json` copied from `assets/blueprints/blueprint-bundle.json`, **this release's** `timeline-full-widget-4.0.0.zip`, and both sample `.tfw.json` files. This bundle uses the official `bundled` resource reference and installs this exact ZIP. Always check both JSON recipes and fixture privacy. A successful static validation is not an actual Playground browser smoke test.

## 5. Gutenberg and saved-content safety

- Synchronize `block.json`, `src/index.js`, `src/item/index.js`, `src/item/areas/`, attribute schemas, and both `edit`/`save` implementations.
- Treat Gutenberg's saved HTML and block comments as a compatibility contract. Changes to `save()` may invalidate existing posts. Prefer minimal saved markup, semantic CSS fallbacks, and supported `deprecated` + `migrate` definitions for intentional changes.
- Preserve title/side/content migration behavior and `getLegacyTemplateProps` compatibility. Never remove old attributes or migration code solely because they are absent from current controls.
- After changing block markup or nested templates, inspect `assets/blueprints/blueprint.json`. It currently installs **the WordPress.org release**, not local source; therefore it cannot by itself validate unpublished changes. Use a locally installed ZIP for unpublished integration tests and verify the demo `post_content` opens without the “unexpected or invalid content” warning.
- `block.json` `textdomain`, PHP header and translatable PHP/JS strings now consistently use `timeline-full-widget` (fixed in 3.3.6). `za/...` block names, `za-timeline` widget ID and `za-` script handles are **persistent technical identifiers**, not translation domains. Never rename them to fix i18n.
- `assets/js/adapters/classic-adapters.js` resolves its animation import relative to `import.meta.url` when explicit editor configuration is absent. Do not reintroduce a hard-coded `/wp-content/plugins/` URL (sites may use a custom content directory, symlink, or CDN). Its parent-frame fallback supplies configuration inside TinyMCE's iframe.

## 6. PHP, security, and asset rules

- Follow WordPress Coding Standards and WordPress security conventions: capabilities, nonce validation for writes, input validation/sanitization, escaping output, safe queries, and translation context.
- Keep actual PHP classes in `includes/` with one matching namespace/class/file path per PSR-4. `TimelineFullWidget\` maps to `includes/`; e.g. `TimelineFullWidget\Assets\AssetManager` maps to `includes/Assets/AssetManager.php` (case-sensitive). Avoid dumping procedural code into class files.
- **PSR-4-style autoloading and WordPress Coding Standards are separate concerns**; PSR-4 does not imply PSR-12 formatting. Do not introduce Composer solely to satisfy PSR-4. Existing `includes/Autoloader.php` and bootstrap remain valid unless requirements change.
- New namespaced classes belong in the matching directory. Global hooks/functions/constants must be appropriately prefixed. Preserve deliberate compatibility exceptions in the two root PHP files.
- WordPress APIs and Elementor APIs are not available in plain CLI tests. Guard Elementor-dependent code; avoid class-loading `TimelineWidget` before Elementor's base class exists.
- Keep asset registration/loading in `includes/Assets/AssetManager.php`: `block.json` owns Gutenberg compiled styles/scripts; Elementor depends on registered `timeline-core-style`, its widget script and preview integration; Classic uses its editor adapter. **Register once** in `registerAssets()`; `enqueueElementorEditorAssets()` should only enqueue existing registered handles. Frontend Gutenberg JS is conditionally enqueued based on the parent block. Keep module `type` handling and script dependencies intact.
- Classic Editor integration must not enqueue on dashboard/taxonomy screens or on new Gutenberg posts without IDs. Probe the actual post when present and otherwise use screen/post-type block editor APIs. TinyMCE toolbar registration must honor user editing capability and rich-text configuration.
- Elementor PHP `render()` and Underscore `content_template()` must have consistent title tag fallback: requested `a` with no URL renders a `div` with `.tl-title`. Both must escape titles and keep valid link attributes.

1. **Scope/diff:** inspect modified files and `git diff --check` (when in a Git checkout); confirm no unrelated code or obsolete flags were added. Identify whether a suspected `legacy` path is reachable through saved WordPress posts, custom integrations or earlier shortcodes; do **not** remove migration code merely for being old.
2. **Dependency-free regressions:** run `node scripts/tests/js-runtime.mjs`, `node scripts/tests/transfer.mjs`, `node scripts/tests/transfer-ui.mjs`, `php scripts/tests/php-runtime.php`, `php scripts/check-release.php`, then `php scripts/check-blueprint.php` (or `npm test`, which also finishes with PSR-4). Keep tests updated alongside changes to public CSS variables, DOM classes, inheritance behavior and Elementor render parity. These tests are **not** full WordPress integration tests.
3. **JS/CSS changes:** after `npm ci`, run `npm run check` and `npm run build`. Review warnings and changes to `build/index.js`, `build/index.asset.php`, and generated CSS. Normally regenerate `build/` via `npm run build`; never assume hand-edited minified bundles prove build correctness. The 4.0.6 hotfix appended matching narrowly scoped placeholder CSS to `build/style-index{,-rtl}.css` because npm dependencies were unavailable. This is a known unverified build exception: re-run `npm ci && npm run build` and verify updated sourcemaps before production; explicitly report NOT RUN for the build now.
4. **PHP syntax:** lint **all** shipped PHP files (not only classes):

   ```sh
   find . -type f -name '*.php' -not -path './node_modules/*' -print0 | xargs -0 -n1 php -l
   ```

5. **PHP/WPCS:** run `phpcs` with the project's applicable WordPress ruleset *if available*. If PHPCS/WPCS is absent, record `NOT RUN`; PHP syntax success is not a coding-standards audit.
6. **Manual WordPress smoke:** activate with Elementor disabled; then test with Elementor enabled. Insert two+ Gutenberg items; test style copy, newly inserted item inheritance and independent edits; save/reload a previously created 2.x/3.x page; verify frontend, narrow Columns, RTL where relevant, responsive styles, animation teardown, Elementor frontend vs live preview, and Classic integration if affected. A CLI-only pass does **not** replace these tests.
7. **Docs/release:** update `CHANGELOG.md` for behavior changes; update `readme.txt` when features, compatibility, screenshots, or upgrade notes change. For releases synchronize the plugin header, `TIMELINE_FULL_WIDGET_VERSION`, `package.json`, `package-lock.json`, readme Stable tag, and changelog; run `php scripts/check-release.php`. No version bump is required for an AGENTS-only update.
8. **FINAL REQUIRED GATE — PHP plugin structure / PSR-4-style:** run this **last**, after any refactor and before reporting completion:

   ```sh
   php scripts/check-psr4.php
   ```

   `npm test` executes this as its **last** subtask. For a complete audit, run the explicit command again **after** any remaining modifications. It checks all `includes/**/*.php` class declarations against the `TimelineFullWidget\` namespace-to-path mapping, exact filename case, one class/interface/trait/enum per file, bootstrap/autoloader presence, and smoke-loads classes that do not require Elementor. `TimelineWidget` is checked structurally but not instantiated in plain CLI because it extends Elementor. A nonzero exit means **FAIL**; fix the mapping before release. This is a *PSR-4-style structure gate*, not a substitute for PHPCS, PHPUnit, a real WordPress activation test, or Composer validation. If PHP is unavailable, explicitly report **NOT RUN** rather than passing the gate.

## 8. Agent delivery expectations

- Prefer small, attributable edits over architectural rewrites. Before adding duplicate helpers/controls, check both builders and their shared CSS/animation contract.
- State which commands actually ran and their results. Explicitly separate static checks, builds, and tests requiring an actual WordPress/Elementor site.
- Note required migrations and compatibility risks. Do not claim a common persisted style schema or synchronized settings exists until it is implemented and tested.
- Do not modify WordPress.org graphics or unrelated release files for a coding-guide change.
- Release ZIP (developer archive) should contain source, `build/`, `AGENTS.md`, tests and scripts, without `node_modules/`, temporary files, or npm installation failures. WordPress.org deployment uses `.distignore` and deliberately excludes development-only `AGENTS.md`, `src/`, `scripts/`, and Node dependencies.
- **Known limits / deferred debt:** `src/style.scss` still mirrors some shared CSS declarations for Gutenberg. Consolidate these only together with a successful `npm run build`, updated assets, and editor/frontend visual comparisons; avoid deleting one source while leaving the generated bundle stale. `src/block-template-compat.js`, saved-block deprecations and compatibility aliases must remain while older supported WordPress installations and saved content exist. There is now a common portable file format, but not a shared *persisted* cross-editor style schema. Same-editor import is supported; compatible bidirectional cross-editor conversion is supported but not lossless (Advanced CSS, theme fonts and arbitrarily nested content still require manual attention). A local CLI audit cannot certify browser layout, PHP/WPCS, WP.org Plugin Check, or WordPress/Elementor integration.

## 9. Transfer parity additions in 4.0.6

- **Both directions:** `parseTransfer()` accepts either `origin` for either editor, validating before conversion. `prepareImport()` converts Elementor to Gutenberg via `elementorToGutenberg()`; the existing `gutenbergToElementor()` maps in the reverse direction. Native imports preserve native settings. Never rename stored controls or block attributes.
- **Elementor per-item layout (current):** repeater `item_content_layout` is an independent on/off `SWITCHER` (`horizontal` = on, `''`/`vertical` = off) and `tl_card_change_direction` is an independent on/off switcher (`yes` = on). Both default off for new items, even when `inherit_item_styles = yes`. Shared style inheritance only affects visual styles, not layout/media order. Global Elementor layout switches no longer exist in the UI. PHP `render()` and JS `content_template()` must agree on effective per-item values and CSS classes (`tl-content-horizontal`, `tl-reverse`).
- **Old Elementor content and transfer compatibility:** existing saved widgets may still carry `tl_content_horizontal_layout` / `shared_reverse_media_content`. The renderer reads those historic values *only for items without an explicit item flag*. `normalizeElementorItemLayouts()` is the sole transfer migration boundary: import/export migrates older JSON to item-level flags and removes old global fields. Never reintroduce global UI or couple the new switches to `inherit_item_styles`. Do not delete this narrow compatibility path until an explicit content migration exists; otherwise older published Timeline layouts would change.
- **Media:** blank `media_image`/`marker_image`/`posterURL` controls must stay blank, never become fabricated SVGs. Placeholder URLs are local. The shared CSS must constrain placeholder marker images to `--marker-size` despite the legacy `.tl-mark img { max-width: initial !important; }` rule. Maintain the corresponding prebuilt Gutenberg CSS until a successful `npm run build` regenerates it.
- **Block conversion:** Elementor repeater items become `za/timeline-item` with `za/timeline-item-side` and `za/timeline-item-content`. Support safe `<p>`, `<h1>`…`<h6>` and list structures using native `core/paragraph`, `core/heading`, `core/list` and `core/list-item`; preserve text/links, heading type and basic typography. Do not claim arbitrary Elementor fonts, Advanced CSS, complex nested HTML or arbitrary Gutenberg blocks map without loss.
- **UI regression:** each shared popup starts with fresh `IMPORT_OPTIONS` (or `content:false` for older files with missing content); old choices must not leak into subsequent imports. Gutenberg file picker must accept both `data.list` and `data.innerBlocks`; item count and warnings belong in the popup, not the inspector sidebar. Test both source types through the *actual sidecar handler*, not just `prepareImport()`.

## 10. 4.0.0 cross-editor regression safeguards

- Gutenberg main-content toggles save through `setTimelineItemAttributes()` into both the parent item and its nested content area. Existing exports may contain contradictory values. The **parent item flag is authoritative** in cross-editor conversion; use nested flags only when the parent has no explicit boolean flag. Gutenberg→Elementor must always write repeater-level layout switches and must not set visual-style inheritance to `no` solely for layout. Do not use the child's default `false` to erase a parent `true`.
- Gutenberg main content has arbitrary ordered InnerBlocks. In the Elementor adapter the first authored text block (or an explicit `.tl-title`) becomes the Elementor title; other blocks remain in their original order in the HTML body. The opposite-side block hierarchy must map to `side_content` only. Elementor repeaters cannot represent arbitrary nested Gutenberg structures; avoid claiming pixel-perfect fidelity.
- Elementor `list_title` is always mapped to a Gutenberg heading, even if Elementor's `header_tag` is `p` or `a`. This avoids the Gutenberg area-migration logic inserting a second implicit title. Embed validated `title_link_url` in RichText heading content; preserve existing safe HTML anchors from `list_content` independently.
- Elementor widget-level `_background_background`, `_background_color` and `_background_image` must map to the registered `timelineBackground*` root attributes, never overwrite card background. Never embed a donor URL; only use the destination-local placeholder. `getTimelineWrapperStyle()` enforces sanitized background colors and URLs. Native Elementor → Elementor keeps all original Advanced controls.
- Marker activation is driven by animated line progress and actual viewport scrolling, not editor selection/closest item. Keep the event cleanup and MutationObserver refresh in both source and runtime bundle. Live inspector changes of marker color/size must refresh the geometry. Test before and after editor re-render and compare with saved front end.
- **Build note:** 4.0.0 includes a narrowly patched prebuilt `build/index.js` because wp-scripts dependencies are not installed in this environment. Its obsolete source map was removed. The next build engineer must run `npm ci && npm run build`, inspect generated assets, and verify migration compatibility and DOM behavior in actual WordPress + Elementor. Do not count static tests as a successful browser test.

## 11. Gutenberg iframe animation and toolbar integration

- In the Gutenberg iframe, the Timeline may be scrolled by the iframe itself, its surrounding editor canvas scroller, or both. Do not use `parentWindow.innerHeight / 2` as the animation trigger: the top Gutenberg toolbar and editor panels shift the visible canvas. Determine the visible rect as the **intersection** of the iframe rect, the outer window viewport, and every overflow-clipping ancestor of `window.frameElement`, then measure the Timeline in the same parent-coordinate space. If an inner node truly scrolls, use its local viewport, not parent coordinates.
- A CSS `overflow-y:auto` container without overflow (`scrollHeight <= clientHeight`) is not an active scroll root. The Gutenberg-only `assets/js/adapters/gutenberg-editor-scroll-bridge.js` forwards outer editor scroll events to the iframe; retain it until iframe scrollers and real WordPress versions are checked. Neither the bridge nor parent scroll listeners should be injected into Elementor/frontend pages.
- `src/edit.js` imports `initTimelineAnimation` from `assets/js/core/animation.js`; the generated `build/index.js` includes that code, so changing only the standalone module **does not** repair Gutenberg. Preferred workflow is `npm ci && npm run build`, which regenerates `build/` and `build/index.asset.php`. Any emergency manual bundle patch must be documented, syntax-checked, smoke-tested in a browser and have its `build/index.asset.php` version changed to prevent stale assets. No stale sourcemaps should be distributed.
- Direct `ToolbarButton` and `MediaReplaceFlow` components must be nested inside `ToolbarGroup` within `BlockControls` rather than rendered as custom direct toolbar controls. Keep source and built output synchronized. Do not patch WordPress core API warnings or enqueue arbitrary style handles in the Gutenberg iframe to silence diagnostics.
- Console diagnostics: `core/edit-post.isEditorPanelEnabled` deprecation and `api-fetch` preload messages originate in WordPress/editor integrations, not the Timeline code shown here. `elementor-admin-css` belongs to Elementor; `global-styles-css-custom-properties-inline-css` comes from WordPress global styles. Trace a stack/initiator before attributing those warnings to this plugin. `Using custom components as toolbar controls` can be triggered by plugin-authored controls and warrants a toolbar structure audit.
- Required regressions: iframe-local scrolling, parent editor canvas scrolling, clipping by top/bottom editor chrome, live inspector changes of animation color, toggling animation on/off, marker activation timing, independent frontend behavior, and listener teardown on block remount. Pure JS tests plus isolated Chromium are useful, but a working WordPress/Gutenberg in-browser test remains required to certify integration.

## 12. Gutenberg animation lifecycle and no-event scroll diagnostics

- `src/edit.js` must initialize exactly the wrapper owned by its React component; do not invoke `initAllWidgets()` from each React Timeline instance. `initAllWidgets(doc)` remains the safe document-wide entry point used by the Classic, Elementor and frontend Gutenberg adapters. Its `__zaTimelineDestroy` guard prevents duplicate active listeners, even if it is called more than once.
- Do not add `innerBlocks.length`, marker color, marker size, or other presentation props to the Gutenberg animation effect dependencies. Such dependencies destroy/recreate the animation on every inspector edit or added child, which resets the line to zero and makes scroll appear to work only briefly after an insertion. `MutationObserver` refreshes child marker references and CSS variables update presentation without restarting the lifecycle.
- Gutenberg iframe scroll and parent editor scroll can fail to emit an event into the animation realm. In the Gutenberg editing canvas only, `assets/js/core/animation.js` uses a low-frequency (100 ms) **geometry change detector**. It compares Timeline bounds, visible viewport and the parent iframe's top coordinate, starts the ordinary rAF animation only when these measurements change, and removes the interval on destroy. The frontend and Elementor must not poll geometry.
- Do not drop `window.frameElement.getBoundingClientRect().top` from this signature. When an oversized iframe moves inside an editor scroller, the iframe's clipped viewport and the Timeline's *local* bounding rect can stay constant while their relative position changes.
- Avoid a global Gutenberg `overflow-x:hidden`; it may change sticky/scroll behavior. The editor-only `src/editor.scss` constrains Timeline descendants and clips only Timeline's horizontal overflow with `overflow-x:clip`. Corresponding runtime styles in `build/index.css` / `build/index-rtl.css` must remain synchronized.
- `assets/js/adapters/gutenberg-editor-scroll-bridge.js` is a best-effort event optimization only; Timeline animation must still advance if that bridge emits no event. The bridge must never create horizontal or vertical scrolling or run on the frontend.
- Regression tests: `scripts/tests/animation-scroll.mjs` covers iframe-local scroll, parent scroll, zero scroll-event geometry changes, repeated init and cleanup; `scripts/tests/js-runtime.mjs` checks the shipped webpack bundle. To claim production parity, additionally test on an actual WordPress editor with the animated line, selected and unselected items, and an Elementor-generated page as a separate case.
- `elementorFrontendConfig is not defined` originates from Elementor's own `frontend.js`, not from the Timeline module (which never reads the variable). Diagnose Elementor's registration, inline settings, cache and script-order environment before altering Timeline's dependency list. Do not create dummy Elementor globals to silence the error.
- Build warning: when `npm ci` / `wp-scripts build` cannot complete, any emergency changes to `build/index.js` must be narrow, reviewed against the canonical source, covered by tests, and accompanied by an updated `build/index.asset.php` content hash. Perform a clean `npm ci && npm run build` with supported Node LTS as soon as possible and confirm generated files retain the watcher and editor CSS.
